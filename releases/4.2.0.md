## What this release is about

An asset and its configuration item can now be linked, so the machine in Assets and the same machine in the CMDB know about each other. FreeITSM can also discover Hyper-V hosts and Failover Clusters, and build the CMDB from them. When a cluster node fails, impact analysis now tells a VM that will fail over apart from one that will simply go down, and always lists what it cannot know. The Servers page counts the hosts and clusters of every source, and there is demo data so you can try all of it without a real Hyper-V estate.

## New features

- **Link an asset to its configuration item.** The asset shows a Configuration item card, and the CI shows an Asset card, with the link's history on both. Linking needs the right to change both Assets and the CMDB. Someone who cannot open the other side sees only that the record is linked to a restricted one, never its name. CMDB → Settings → Asset card chooses which asset details a CI shows. Thanks to @Dr4inder for the request and a very careful review of the design ([#201](https://github.com/edmozley/freeitsm/issues/201)). Details: [Linking an asset to its configuration item](https://github.com/edmozley/freeitsm/wiki/Asset-CI-Link).
- **Create linked CI.** Map an asset type to a CMDB class (Assets → Settings → Asset types), and an asset of that type can make its own configuration item in one click. If a CI with the same name already exists, it offers to link that one instead rather than making a duplicate.
- **"If this failed" on an asset.** A linked asset shows its configuration item's impact - how much depends on it - with a link to the full analysis.
- **Hyper-V and Failover Cluster discovery.** A read-only PowerShell collector runs on one of your Windows servers and sends its hosts, clusters, roles and VMs to FreeITSM, so it works with Docker on Linux too. Set up connections in Assets → Settings → Hyper-V. A VM that stops being reported is marked "not seen", never deleted. Live migrations keep the same record. A machine that comes back with a new identity waits for you to decide whether it is the same machine. Before sending anything, `-TestAccess` shows what the account can and cannot read, and `-Redact` produces a report with names and addresses replaced. The collector has been tested against simulated hosts only and has not yet run on a real Hyper-V estate, so I would be glad to hear how it goes on yours. Thanks again to @Dr4inder ([#199](https://github.com/edmozley/freeitsm/issues/199)). Details: [Hyper-V and Failover Cluster discovery](https://github.com/edmozley/freeitsm/wiki/Hyper-V-Discovery).
- **Build the CMDB from discovery.** Each Hyper-V connection can create and keep up to date configuration items for its clusters, hosts and VMs, using your own classes and relationship types. A preview comes first, and a CI with the same name is offered as a match to confirm, never taken over by name. Discovery never changes a CI's properties or the relationships you drew yourself.
- **Impact analysis that understands clusters.** Mark a relationship type as redundant membership or placement with failover, and "If this failed" grades everything above a failed node as affected, may be interrupted, redundancy reduced or unknown. It always lists what it cannot know, such as quorum, storage and capacity. A VM that is not a clustered role is affected when its host fails, and a hard dependency is never softened by a possible failover. CMDB → Settings → Impact chooses what a cluster member with no recorded state counts as.
- **Hyper-V on Background jobs.** Each connection is listed and goes late or overdue if its reports stop arriving.
- **REST API** for the asset and CI link (with its own narrow permission, so an integration can maintain links without editing records), and for sending and checking Hyper-V reports.
- **Virtualisation demo data.** System → Demo Data → Virtualisation adds a Hyper-V cluster, a Proxmox cluster, a Cloud Director organisation and some vCenter VMs, built into the CMDB with assets linked. It has its own Remove button.

## Improvements

- **The Hosts and Clusters cards on Assets → Servers count every source** - Hyper-V, Proxmox and the ESXi hosts behind vCenter. Click either one for a view of each source's clusters and hosts with the VMs on each, then click a host to list only its VMs.
- **Merging two assets keeps their configuration item links.** If both were linked, the merge window asks which link to keep, and cancelling leaves everything as it was.
- **The "show PHP errors" switch works in Docker**, set from the environment, and is documented in the installation guide.

## Fixes

- **The ESXi Hosts card on Assets → Servers nearly always read 0**, and the Clusters card counted Cloud Director data centres as clusters.
- **Deleting a configuration item left asset custom fields pointing at it**, shown as a bare number.
- **Editing a company's own asset type lost its icon and reset its layout** when saved.

## Upgrading

1. Pull the new code, or rebuild the Docker image.
2. Sign in as an administrator and run **System → Database Verification**. It adds the tables for asset links and Hyper-V discovery, and a few columns.
3. Hard-refresh your browser (Ctrl-F5). This release updates cached scripts on the Assets, Servers and CMDB pages.

Things to know:

- There are three new settings permissions: Assets → Hyper-V, CMDB → Impact and CMDB → Asset card. Administrators have them already. Give them to a role if anyone else should manage these settings.
- Hyper-V discovery needs the collector scheduled on a Windows server. The guide linked above walks through it, including the minimum read permissions.
- The new screens are in English for now in eight languages; translations follow.

## Rollback

Safe. This release only adds to the database, so you can go back to 4.1.0.
