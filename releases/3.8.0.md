## What this release is about

Change Management can now be the record an auditor relies on. Every approval is kept as a round tied to the exact content it was given, every version of the long text is kept in full, and a new **Enforce approvals** setting stops a change being implemented without a current, independent approval - on screen and through the REST API alike. Approvers no longer need more access than the job, reviewers can be given **Read only** access, and routine work can be pre-authorised by an approved template. **Nothing changes how your team works until you choose it:** every new rule is a setting whose default is today's behaviour. This release also fixes two security issues, so please upgrade. Built from [#180](https://github.com/edmozley/freeitsm/issues/180), raised by a supporter of the project after evaluating FreeITSM for a small IT team.

## Security

- **Text in a change could run script for whoever opened it.** An analyst with Change Management could put script into a change's description, plan or review text, and it ran in the browser of anybody who opened the change or exported it to PDF. That text is now cleaned before it is shown, everywhere it is shown. Affects earlier versions.
- **Any analyst with Forms or Workflow could change that module's AI settings,** including the API key and where the AI requests are sent - although testing the key needed the AI settings permission. Saving them now needs that permission too. If analysts who should not have had it use Forms or Workflow, check **Forms → Settings → AI** and **Workflow → Settings → AI** still hold the provider and key you expect.

Neither needed anything beyond upgrading.

## New features

- **Approval rounds.** Submitting a change opens an approval round that keeps a snapshot of exactly what was submitted. It closes as approved, rejected, withdrawn or superseded, and every vote is kept. The change's new **Approval** panel shows the current round, who has voted, and the earlier rounds - so the history reads "approved, then edited, then approved again". A change approved by hand is recorded as approved by hand, and changes that were already approved when you upgrade are marked as approved before records were kept.
- **The named Approver can approve.** Until now the Approver field was a label. The approver now gets **Approve** and **Reject** on the change, with a note.
- **Votes name the version they were cast on.** If somebody edits a change while an approver has it open, a vote from the out-of-date page is either recorded and marked "cast against an earlier version", or refused - the approver is shown what changed and votes again.
- **Enforce approvals** (Change Management → Settings → **Approvals**). A change cannot reach Approved, Implementing or Done without a current approval, through any route - the edit form, the right-click menu or the API. Submission is refused when nobody independent could decide it, the approvers are fixed once a change is submitted, a requester's or assignee's own vote is recorded but not counted (administrators included), and editing what was approved sends the change back for approval. Changes of a type marked **Emergency - approve afterwards** may go ahead first and are flagged on Watchtower until they are decided. An optional administrator override needs a written reason, which is recorded.
- **The Approvals tab** holds all of these rules, each a dropdown or a tick: Record or Enforce, approving your own change, who counts as the change's own people, which fields need a fresh approval when edited, what happens to an approval after an edit, out-of-date votes, deleting submitted changes, where a rejection and a cancellation go, and who may choose approvers.
- **Every version of the long text is kept.** Each save of a description, reason, risk, test plan, rollback plan or review keeps the whole text, with who saved it and when. The timeline shows "edited the Test plan - View", each section has a **Versions** link, and a viewer compares any two versions word by word or side by side. Text that existed before the upgrade is labelled "as found when history began" - never presented as the original. Attachments are now recorded when added or removed, with a fingerprint of the file, and a deleted comment is kept as evidence.
- **Export evidence**, on the change's share menu: one printable page with the change, every approval round and vote, every text version in full, the audit trail and comments, and the attachments with their fingerprints. Taking a copy is itself recorded.
- **Cancel instead of Delete.** Settings can stop a submitted change being deleted (Enforce always does): it is cancelled instead, and keeps everything. A draft that was never submitted can always be deleted.
- **Standard changes from approved templates** (Change Management → Settings → **Templates**). Write a recipe for routine work once - with what it is for and not for, which fields are completed per change, and which teams may use it - and have it approved by somebody else. A change raised from an approved template with its wording untouched is pre-authorised by that approval, and the record says which template version and who approved it. Change the wording and it goes to normal approval. Off until you switch it on in the Approvals tab.
- **Read only access** for Change Management and Forms (System → **Modules**). A reviewer can read everything - records, approval history, text history, exports - and change nothing, on screen or through an API key acting as them. A read-only analyst named as an approver can still approve.
- **Approvers no longer need the Forms module.** Somebody named as a form's approver can open **Form approvals** from the launcher and decide their own requests, without seeing the designer or anybody else's submissions.
- **Everyday permissions in Roles.** Roles can now hold **Choose approvers**, **Design forms** and **Approve standard-change templates**, shown under "Everyday work". The first two only take effect when you switch them on (Change Management → Settings → Approvals, and Forms → Settings → **Access**), so nobody loses anything by upgrading. Forms' Access tab lists who would keep designing before you switch.

## Improvements

- **Statuses have a stage** (Change Management → Settings → Statuses): Draft, Awaiting approval, Approved, Implementing, Done or Stopped. Approvals go by the stage, so a status can be renamed without breaking voting. Closed now follows the stage, and a status with no stage is marked so you can choose one.
- **New workflow triggers** for a change being submitted, sent back for approval, rejected, or having its approval withdrawn - so a rule can tell the board when a change needs their vote. "A change is approved" now says how it was approved.
- **REST API:** new endpoints for a change's approval rounds, the approver's decision, cancelling, and the text history, with new permissions that start unticked on existing keys. A change now carries its current approval and its status's stage.

## Fixes

- **A change approved by hand was never marked as approved,** so Watchtower counted it as awaiting approval for ever and a Projects "change approved" gate never ticked.
- **After a required CAB member rejected a change and it was resubmitted,** the next vote by anybody sent it straight back to Draft.
- **Renaming the Approved or Pending Approval status broke CAB voting** - a deciding vote left the change with no status, and the Approvals page emptied.
- **Two last CAB votes arriving together could send the "approved" workflow event twice.**

## Upgrading

1. Pull the new code, or rebuild the Docker image.
2. Sign in as an administrator and run **System → Database Verification**. It adds the approval and text-history tables and a few columns, gives your existing statuses their stage, and records your changes that are already past submission as approved before records were kept (changes awaiting approval keep their votes).
3. Hard-refresh your browser (Ctrl-F5) - this release updates cached JavaScript and stylesheets.

**What you will notice straight away:** Watchtower's "awaiting approval" count now counts only changes in an Awaiting approval status, so it may go down. If you have renamed or added statuses, open **Change Management → Settings → Statuses** and choose a stage for any marked amber - Enforce cannot be switched on until every active status has one.

## Rollback

Safe - this release only adds to the database, so you can go back to 3.7.0 with the code alone.
